0. 结论速览

这是一个架构成熟度明显高于平均水准的 Android 工程：分层严格（core/data/di/domain/framework/ui/util 七层， 职责边界清晰）、依赖集中管理（Version Catalog + convention plugin + FAIL_ON_PROJECT_REPOS）、 Koin 注入规范、Compose + Room3 + Flow 全线现代栈。

但它不是普通 App：它的核心业务是「调用系统最敏感的那部分 API 去装包」， 因此真正的复杂度集中在三处 —— 特权执行后端（Root / Shizuku / Dhizuku / app_process / 系统 PM 五套并存）、 安装包解析引擎（APK/APKS/APKM/XAPK/ZIP 五种容器 + 模块包）、以及 会话状态机（前台服务 + 通知 + Live Activity）。 这三处也是最容易出问题的地方。

当前分支上的工作重点是代码优化计划（32 项待办，P0 6 项）与 Miuix UI 家族移除， 移除正在进行中且已推进过半。构建已实测通过（见 §1）。

3. 核心内核之一：特权执行后端

这是整个项目最敏感、也最能体现设计水准的部分。它没有把五种授权方式写成五份 if-else， 而是抽象成 授权者（Authorizer）→ 执行器（Executor）→ 运行时（Runtime） 三段式。

3.1 能力契约

所有后端统一收口到一个接口上（PrivilegedOperations.kt，31 行，纯声明）：

interface PrivilegedOperations {
    fun delete(paths: Array<out String>)
    fun performDexOpt(packageName: String, compilerFilter: String, force: Boolean): Boolean
    fun setDefaultInstaller(component: ComponentName, enable: Boolean)
    fun startActivityPrivileged(intent: Intent): Boolean
    fun sendBroadcastPrivileged(intent: Intent): Boolean
    fun execArr(command: Array<String>): String
    fun execArrWithCallback(command: Array<String>, listener: ICommandOutputListener?)
    fun setAdbVerify(enabled: Boolean)
    fun grantRuntimePermission(packageName: String, permission: String)
    fun isPermissionGranted(packageName: String, permission: String): Boolean
    fun getUsers(): Map<Int, String>
    fun getSessionDetails(sessionId: Int): Bundle?
    fun setPackageNetworkingEnabled(uid: Int, enabled: Boolean)
    fun prepareUnknownSourceAppOp(uid: Int, packageName: String): Int
}
设计亮点：注释明确写了「Binder hook 后端直接使用此接口，只有真正需要跨进程的操作才另外暴露到 IPrivilegedService」。这是一个刻意的最窄暴露面——能同进程做的绝不开 Binder 通道。 在特权代码里这是正确的取向。

值得注意：infrastructure/recycler/ 下有 5 个 Recycler 实现 —— 说明「进程/UserService 复用」是被当作一等公民处理的（冷启动开销是这类应用的主要性能瓶颈）。 但这也意味着生命周期管理的表面积很大，优化计划里的 P0 #1「CoroutineScope 泄漏」恰好就落在 AppInstallerRepositoryImpl 与 IBinderAppInstallerRepoImpl 上。二者相关，不排除是同一个根因的两个面。

4.2 安装选项（Install Flags）

InstallOption.kt 用枚举 + minSdk/maxSdk 显式表达了 20 个 INSTALL_* 标志的可用区间， 每个都带 @StringRes 标签与描述。这个设计很干净 —— 版本门禁写在数据里而不是散落在 UI 条件判断里。 其中 External 在 P 以上失效、DryRun 限定 Q~R、BypassLowTargetSdkBlock / RequestUpdateOwnerShip 等只在 API 34+ 出现。

5. 核心内核之三：会话与流式安装

5.2 网络访问边界 已证实

AGENTS.md 把「网络访问边界」列为关键约束：APK 可以声明 INTERNET 权限， 但当应用内网络开关关闭时，网络请求必须保持禁用。我在代码里确认了这个约束是真的被执行的：

// OkHttpNetworkResolver.kt:94-100
val preferences = appSettingsRepo.preferencesFlow.first()
if (!preferences.allowInternetAccess) {
    throw ResolveException(
        errorType = ResolveErrorType.NO_INTERNET_ACCESS,
        message = "Internet access is disabled in app settings.",
    )
}

位置正确 —— 在 resolver 入口处、任何建连动作之前先 fail-fast， 而不是靠 UI 隐藏入口。Manifest 里 INTERNET 与 ACCESS_NETWORK_STATE 已声明， 并配了 network_security_config。

9. 总评

做得好的

  • 分层严格且被实际遵守（domain 不含 Android UI 工具，data 不含展示逻辑）
  • 依赖全走 Version Catalog；convention plugin 抽公共 Gradle 逻辑
  • 特权后端抽象干净：单一能力契约 + 多授权者实现，能同进程做的不开 Binder
  • 容器解析用 Strategy 模式，新增格式成本低
  • 网络开关是真执行而非仅 UI 拦截，fail-fast 位置正确
  • InstallOption 把 SDK 版本门禁写进数据而非散落 UI 判断
  • 文档体系完整：AGENTS.md / CONTRIBUTING.md / docs 多语言 / 1810 行优化计划

值得改进的

  • P0 的 6 项里有 3~4 项同源（生命周期未绑定 owner），宜合并审计
  • Process.join() 无超时 —— 特权路径上这是挂死风险，优先级应最高
  • 文档与实现脱节（Miuix），违反了仓库自己的规则
  • ActionHandler.kt(1035) / DefaultPrivilegedService.kt(1008) / InstallerViewModel.kt(1094) / InstallInfoDialog.kt(1083) 四个千行级文件，拆分收益明显
  • 工作区有一个未提交、未验证的改动
  • 仓库内混入构建产物
